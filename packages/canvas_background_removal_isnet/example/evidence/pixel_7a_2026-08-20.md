# ISNet Android benchmark decision — Pixel 7a — 2026-08-20

## Decision

**NO-GO for production promotion of this exact 1024x1024 FP16 ISNet candidate.**

The candidate is numerically/visually viable, and strict LiteRT Next GPU fp16 makes inference fast enough to be interesting, but the active GPU memory footprint remains too high for a general Android production provider.

This decision is intentionally narrow:

- it applies to the verified ISNet candidate identified below;
- the existing ML Kit provider package is unchanged;
- it does not rule out a materially smaller/lower-resolution on-device segmentation model in a future PR;
- it does not justify downloader, model-delivery, provider-selection, fallback, or rollout infrastructure for this candidate.

## Candidate under test

- model: `isnet-general-use`
- converted artifact: FP16 TFLite
- size: `88,135,432` bytes
- SHA-256: `325ecf784635a998bd55e3fa622f4bc3a42834a8a4a1e08ed58f147eebdfda0a`
- input: `1 x 1024 x 1024 x 3` float32 NHWC
- primary mask: output ordinal `0`, `1 x 1024 x 1024 x 1` float32
- runtime package: `flutter_litert 3.8.0`
- app build mode: Flutter profile
- physical device: Pixel 7a
- benchmark image: banana/product image selected as `isnet_test_portrait.jpg`

Android version and exact ABI were not captured in the checked-in run record, so this document does not infer them.

## Benchmark method

The benchmark uses the same frozen rembg image pipeline for every engine:

1. display-oriented RGB decode;
2. direct Pillow-compatible Lanczos resize to `1024 x 1024`;
3. resized-image max normalization and `-0.5`;
4. one inference;
5. primary output ordinal `0` only;
6. mask min/max normalization;
7. Pillow-compatible Lanczos resize back to the display-oriented source dimensions;
8. original RGB + alpha PNG composition.

Each engine is opened in a persistent worker isolate. A benchmark batch contains one cold run followed by five warm runs. CompiledModel modes use `TensorBufferMode.hostMemory` and read only output ordinal `0`.

The Interpreter output for the same image is the correctness reference for CompiledModel alpha parity.

Displayed peak RSS is sampled process RSS during each open/run; Android `dumpsys meminfo` was also captured for the final GPU fp16 path.

## Android memory corroboration for GPU fp16

`adb shell dumpsys meminfo com.nijify.isnetbenchmark` was captured around the final GPU fp16 experiment.

### With GPU fp16 open

Key values:

- `TOTAL PSS: 962163 KB`
- `TOTAL RSS: 1037408 KB`
- Native Heap RSS: `76584 KB`
- Graphics: `666940 KB`
- GL mtrack: `594392 KB`

The large footprint is therefore not primarily Java heap or Dart image-buffer memory; Android reports the majority in graphics/GPU accounting.

### After GPU fp16 inference batch

Key values:

- `TOTAL PSS: 1348048 KB`
- `TOTAL RSS: 1422084 KB`
- Native Heap RSS: `204712 KB`
- Graphics: `899836 KB`
- GL mtrack: `827288 KB`

This corroborates the benchmark sampler: the active GPU path pushes process memory well above the level suitable for a general mobile feature.

### After switching engine / closing the GPU worker

Key values:

- `TOTAL PSS: 444187 KB`
- `TOTAL RSS: 515792 KB`
- Native Heap RSS: `61124 KB`
- Graphics: `239352 KB`
- GL mtrack: `166804 KB`

Most of the GPU/graphics footprint is reclaimed after the worker closes. The high-water mark is therefore not evidence of an obvious permanent leak.

That reclaim does not make the candidate production-viable: keeping the GPU engine warm retains a very large active footprint, while opening/closing it for each operation adds roughly seconds of compile/open latency before the approximately one-second removal.

## Decision rationale

The experiment answered the question #1209 was intended to answer:

- the converted artifact identity and tensor contract can be verified on-device;
- the frozen rembg pipeline produces correct transparent output;
- the classic Interpreter is too slow and memory-heavy;
- CompiledModel CPU fp32 is worse;
- strict GPU fp32 is fast but much too memory-heavy;
- strict GPU fp16 is the best operating point and preserves good first-image parity, but still requires an unacceptably high active GPU footprint;
- closing the worker reclaims most of that GPU memory, so the blocker is the operating footprint/compile trade-off rather than an obvious leak.

Therefore this exact candidate should **not** proceed to production model delivery, provider selection, fallback, feature flags, or rollout work.

The representative multi-image suite is intentionally not expanded in this PR because the first-image runtime evidence already establishes a platform-level memory blocker. Quality coverage becomes worthwhile again only after a future candidate demonstrates a viable memory operating point.

## What remains unchanged

- the ML Kit provider package is unchanged;
- Canvas remains provider-agnostic and sees only the existing background-removal port;
- `canvas_background_removal_isnet` remains experimental development/evidence tooling;
- no model binary is committed or bundled;
- model redistribution rights remain unresolved and must still be resolved before any future model distribution.

## Follow-up

Any future ISNet/on-device segmentation investigation should start in a separate PR and use this harness/evidence as the baseline. It should first target a materially smaller operating footprint, for example through a smaller/lower-resolution model candidate, before investing in production delivery infrastructure.

Do not continue optimizing this PR with additional backends or production integration.
